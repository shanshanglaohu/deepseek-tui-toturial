最佳实践

经过生产验证的模式，让 DeepSeek TUI 会话高效、安全且顺畅。

验证优先开发

最重要的实践：行动前先验证。每次工具调用产生你将依赖的结果后，确认输出符合预期。

验证清单

  • 文件读取：确认行号与即将修改的内容一致
  • Shell 命令：检查 stdout，而非仅退出码
  • 搜索结果：确认匹配项是期望的（存在误报）
  • 子代理结果：对一个发现进行直接读取以交叉验证
🚫 不要相信记忆

永远不要凭记忆打补丁。实时工具输出是唯一的真相来源。记忆不可靠，工具输出不会说谎。

提示词工程

DeepSeek TUI 对结构化、具体化的指令响应最佳。模糊的提示词产生模糊的结果。以下是有效做法：

有效模式

  • 命名动作："正在读取模块树"而非"让我看看"
  • 指定输出："返回 3-5 个要点"而非"告诉我关于..."
  • 约束范围："仅在 src/auth/ 中"而非"找出所有 bug"
  • 提供上下文："在 PR #42 的重构之后..."而非"修复这段代码"

模糊 vs 具体：真实对比

❌ 模糊提示词✅ 具体提示词
"帮我做个网站""创建一个单页作品集网站，包含导航栏、英雄区、技能卡片、项目展示和联系方式。深色主题，响应式布局，纯 HTML/CSS/JS。"
"修一下这个 bug""用户点击提交按钮后表单没有反应。请检查 js/form.js 中的 submit 事件处理，确认是否正确阻止了默认行为。"
"优化性能""首页加载时间 3.2 秒。请检查哪些资源阻塞了渲染，优先优化大于 100KB 的图片和 CSS 文件。"
"重构代码""把 src/utils.js 中的 5 个日期处理函数提取到单独的 dates.js 模块，保持原有导出接口不变，更新所有引用。"

复杂任务的提示词结构

  1. 目标：一行目标描述
  2. 约束：不可触碰的边界
  3. 上下文：相关文件、PR、决策
  4. 期望输出：成功的标准

上下文管理

你的 1M token 窗口虽然宽裕但并非无限。巧妙的上下文管理能让会话保持数小时的高效。

缓存感知工作流

  • 批量读取：一次读取 3+ 文件，而非顺序读取
  • 批量工具调用：grep + read + git_status 在一次轮次中完成
  • 追加而非重写：新发现放在末尾
  • 按路径引用："在 auth.rs:42"而非"这是代码..."

何时使用 /compact

当上下文使用率超过 80% 时建议压缩。将其视为硬重置而非微调。系统会保留工作文件和最近的决策。

⚠️ 缓存衰减

关注缓存命中率指示器。红色（<40%）持续多个轮次 = 需要整合。黄色（<80%）= 注意。绿色 = 健康。

委托模式

何时委托给子代理

子代理适用于独立、可并行的工作。好的候选场景：

  • 调查 3+ 个独立文件或模块
  • 从计划中并行实现独立的叶子任务
  • 在主工作同时运行代码审查

反模式

  • 不要委托单文件读取：直接读取更快
  • 不要预先生成依赖项：等待步骤 A 的输出后再生成步骤 B
  • 不要忘记综合：子代理输出需要整合

模式选择指南

场景推荐模式理由
探索不熟悉的代码库Plan变更前需要可见性
小型、定义明确的 Bug 修复YOLO低风险，成功标准清晰
架构重新设计Plan影响大；先审查计划
为现有代码编写测试YOLO边界明确，有安全网
安全敏感的变更Plan执行前必须审查
重复、可信的工作流YOLO信任是挣来的，然后使用

成本管理

DeepSeek TUI 虽便宜，但长会话和大量子代理仍会累积费用。以下方法帮助你控制成本：

成本优化策略

  • 使用 Auto 模式：简单问题自动用 Flash（便宜），复杂问题才用 Pro
  • 提升缓存命中率：追加而非重排消息，保持缓存命中 >80% → 节省约 90% 输入费用
  • 合理使用推理深度：文件读取无需推理（off）；编码用 high；架构设计用 max
  • 批量操作：一次读取 3+ 文件而非逐个读取，减少轮次数
  • 注意子代理数量：每个子代理都是独立 API 调用，控制在必要范围内
  • 定期 /compact：长会话在 80% 上下文时压缩，减少后续 token 消耗
📊 典型成本参考

一个中等复杂度的编码会话（50 轮、含子代理）使用 Flash 模型通常花费 $0.05–$0.20。使用 Pro 模型同等工作量约 $0.50–$2.00。TUI 头部实时显示当前会话总成本。

常见陷阱

对简单任务过度思考

让思考深度与任务复杂度匹配。文件读取不需要深度推理。将深度思考留给调试和架构设计。

串行化独立工作

如果两个操作不相互依赖，将它们批量执行。调度器会同时执行并行工具调用。串行化浪费时间和上下文。

留空的侧边栏

侧边栏显示 Plan / Todos / Tasks / Agents。当这些面板为空时，用户不知道你在做什么。使用 checklist_write 和 update_plan 保持填充。

盲目遵循原计划

每个阶段后重新审视你的计划。阶段 2 仍然合理吗？如果新信息改变了方法，则更新计划。不要遵循在你理解代码之前制定的计划。

不读取就打补丁

在 edit_file 之前始终先 read_file。行号会变化。代码在读取之间可能被修改。你对 10 轮前的文件记忆不可靠。
